# TIGLONの科目区分の取得経路調査

調査日: 2026-10-14（日本時間）

## 結果

1つの学生アカウントで、通常の認証を行い、履修情報・成績の読み取りを確認した。確認した画面・スクリプトから、今期の未評価科目に対する卒業要件上の科目区分を返すAPIは見つからなかった。これはAPIの不存在や、登録期間終了後の取得不能を証明するものではない。

大学の[2026年度学年暦](https://www.u-ryukyu.ac.jp/aboutus/calendar/)では、後学期の登録調整期間は9月30日から10月15日まで。調査時点は期間中である。対象アカウントは指導教員への履修登録の確認依頼後で、追加などができない状態だった。登録画面は確認画面へ転送され、読み取った履修情報の `Open` は `false` だった。したがって、今回の観測は「確認依頼後・編集不可の状態」であり、登録期間終了後の観測ではない。

## 確認した経路

基準URL: `https://tiglon.jim.u-ryukyu.ac.jp/portal/`

| 取得先 | 観測結果 | 今期の科目区分 |
| --- | --- | --- |
| `StudentApp/Regist/RegistEdit.aspx` | `StudentApp/Regist/RegistListConfirm.aspx` に転送。2026年度後期の履修情報を表示 | HTMLに `lblSbjDivName` 要素なし |
| `StudentApp/Regist/RegistList.aspx` | 履修時間割の表示を確認。最初のアクセスでトップへ転送される場合もあり、画面遷移の文脈に注意が必要 | 区分の表示要素なし |
| `00_ReportClass/Report/Regist/StudyEntryCheckPdf.aspx` | 「印刷用ページ」のボタンから特定。今期の履修情報をPDFで取得 | PDFの文字抽出・画像確認とも区分なし |
| `StudentApp/ReferResults/Menu.aspx` の「成績明細の表示」 | 既存 `FetchGrades` と同じフォーム送信で過去の成績を取得 | 今期の講義コードに一致する成績は0件 |
| `00_ReportClass/Report/ResultsReport/ResultsReportPdf.aspx` | 「個別成績表」のボタンから特定。過去の科目区分を含むPDFを取得 | 今期の科目名に一致する行なし |
| `StudentApp/Regist/RegistSearchResults.aspx?day=1&period=2&label=1-2&fac_mode=1` | 既存アプリが利用する科目検索経路を1コマだけ読み取り | 「選択区分」列はあるが、卒業要件上の「科目区分」列なし |
| 履修・成績メニュー、画面のスクリプト、`Portal.js` | ASP.NET WebFormsのフォーム送信・メニュー遷移とPDFへのリンクを確認 | 独自のJSON API・科目区分サービスの参照は見つからず |

履修確認・履修時間割・成績メニューの `__VIEWSTATE` も読み取り、通常のUTF-8文字列として科目区分の記載がないことを確認した。これだけでサーバー内部の保持データまでは判断できない。

## 確認依頼後の候補ウィンドウへの直接アクセス

履修登録画面を先に開かず、ログイン直後に候補ウィンドウへ直接GETする確認を追加した。

```text
GET /portal/StudentApp/Regist/RegistSearchResults.aspx?day=2&period=3&label=2-3&fac_mode=1
```

指定コマの自学部の候補が取得できた。応答の列は「学部名」「講義コード」「科目名」「教員名」「時限」「単位数」「選択区分」「定員」「登録者数」「登録調整方法」「備考」。定員・登録者数・登録調整方法が実際に返り、確認依頼後でも候補を読み取れることを確認した。

この応答には `lblSbjDivName` や「科目区分」、コア・関連・アドバンストなどの記載はなかった。7分割された `__VIEWSTATE` を連結してデコードした2348バイトにも、科目区分のラベルや `SbjDiv` / `Category` のフィールド名は見つからなかった。画面の「選択区分」は、卒業要件上の科目区分として使わない。

科目名の詳細リンクは `Public/Syllabus/DetailMain.aspx?student=1&lct_year=...&lct_cd=...&je_cd=1`。今期科目の学生向けシラバス詳細も直接GETしたが、科目番号・定員・履修登録方法などは返る一方、科目区分の項目はなかった。

このアプリには同じ候補を取得する `kyomu.Client.FetchCandidates` と JSON API `GET /api/me/candidates?slots=火3&scopes=own` が既にある。JSON APIにはこのアプリのログインまたはAPIトークンが必要。今回実サーバーに接続して確認したのはTIGLONへの直接GETで、アプリのJSON APIを起動しての確認ではない。

一方、`internal/academic/lectures.go` の個別講義の空席照会には `!reg.Open` なら候補を問い合わせずに `registration_closed` を返す処理があり、案内文も「登録期間外」となっている。確認依頼後の編集不可と登録期間外を区別できない判定なので、読み取り可否を `Open` だけで判断しない見直しが必要。`FindCandidatesContext` の候補検索にはこの早期終了がない。

この調査後の実装修正で、上記の `!reg.Open` による人数照会の打ち切りを削除した。編集可否と候補照会を分け、編集不可でも人数を照会し、`addable` は `false` とする。候補画面の表・必要列が返らない場合はエラーにし、空の候補一覧としてキャッシュしない。科目区分について取得できたことを意味する変更ではない。

更新したサービス層のCLIから対象の講義を照会し、定員・登録者数・残席が取得でき、`status=live` と `addable=false` が共存することを確認した。関連する academic / kyomu / handler / ui / mcp のテストも通過した。

既存CLIでの読み取り例（認証情報は既存の環境変数または `.env` を利用）:

```sh
go run ./cmd/kyomu-debug candidates 火 3 own
```

## 次に必要な確認

1. 2026-10-16以降、新たにログインして `RegistEdit.aspx` と `RegistList.aspx` の転送先・区分要素を確認する。アプリDBの保存済み区分や成績からの補完を通さず、生のレスポンスを調べる。
2. 履修印刷PDFと成績明細・個別成績表について、今期科目の収録と区分を再確認する。
3. 科目検索画面が期間外にも通常の読み取りとして利用できるか確認する。調査時点では期間中にしか確認していない。
4. 通常の画面に追加の照会・出力機能が現れた場合、その画面が実際に使う取得先を確認する。今回の調査ではそのような区分取得経路は見つからなかった。

年度・時期・所属や個別認定による違いがあり得るため、今回の1アカウントの結果を全学生・全期間の保証にしない。公式な連携APIの有無は大学のシステム管理者への確認が必要。

## 調査範囲

認証、対象アカウントの画面のGET、通常のメニュー遷移、成績明細の表示に相当するフォーム送信のみ。登録・取消・指導教員への確認依頼・成績変更は行っていない。権限の変更、期間制限の回避、URLの総当たりは行っていない。認証情報、Cookie、氏名、学籍番号、成績の個別値はこのメモに含めない。

公開資料: [教務情報（学生向け）](https://rais.skr.u-ryukyu.ac.jp/dc/?page_id=1206)、[成績の確認方法](https://rais.skr.u-ryukyu.ac.jp/dc/?page_id=13937)。成績情報については学内ネットワークでの利用が案内されている。
